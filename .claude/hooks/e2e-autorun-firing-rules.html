When the E2E Hook Fires

Every condition that arms a WhatsApp E2E run, what it selects, which number it drives, and how to turn it off.

The one-line rule

A git commit or git merge on any branch, or a git push to develop/main/staging, arms an E2E run for whichever features the changed files map to — and the Stop hook then blocks the turn once to make you run it.

Does it fire?

Both halves are off entirely if jq is missing or E2E_AUTORUN_OFF=1 is exported.

What you runResultWhy
git commit — any branch, in-scope filesArms targetedPrimary trigger. A commit deploys nothing regardless of branch, so a branch filter would only make it fire less than asked.
git commit — docs-only / out-of-scope pathsSilentZero features selected. The hook exits without writing a marker and says nothing.
git merge → NIETE-Rumi mainArms /niete-e2e allThe develop → main promotion is the one moment the full 99-scenario suite is worth its hours.
git merge — anywhere elseSilentA merge introduces no files of its own, so the selector sees an empty diff.
git push — develop / main / stagingArms targetedThe code is now reachable — the one moment a run actually tests the change.
git push — a feature branchSilentDeploys nothing; a run would spend ~10 min driving the build that was already live.
git pull / git fetchSilentA pull writes the same reflog as a push. The matcher reads what the entry says, not just its timestamp.
commit outside the bot/** scopeSilentOut of scope. Only bot/** (NIETE-Rumi) and tests/features/whatsapp/niete/** count.

What happens, in order

Numbers are execution order, not a checklist.

  1. The command is matchedPostToolUse on every Bash call. Heredocs are stripped first, so a commit message that merely mentions push can't trigger it.
  2. The repo is resolvedEvery cd in the command (later ones first, relative paths resolved cumulatively), then git -C <dir>, then the payload cwd. An explicit cd or -C wins outright. Only if none exists does the tie-break below apply.
  3. Tie-break: whichever repo was pushed in the last 120 secondsThe reflog entry must literally read update by push. This is an observation, never an override of an explicit instruction.
  4. Changed files are readCommit → git show --name-only --format= HEAD. Push → the tracking ref's reflog range, because after a push @{upstream}...HEAD is empty.
  5. Files are mapped to featuresHand-maintained feature-map.yaml. One file can select several — exam-checker.handler.js selects training and coaching. An in-scope file matching nothing is reported unmapped and the SAFE subset runs as a fallback; under-selection is never silent.
  6. The Gherkin is synced to the diff — before anything is drivenspec_sync.py turns that same selection into a brief (changed files, a bounded diff, the scenarios the spec has today, and create/update/validate-only). The agent authors against it via /sync-specs, using gherkin-test-cases — the same skill /testcases runs. It never deletes a scenario: behaviour that has gone away is tagged @obsolete with a reason and raised as an ask. Then validate_specs.py gates the run — exit 1 and phase 2 does not happen. Without this the suite drove whatever scenarios happened to be on disk, so a commit that changed a flow tested the spec written for the old flow, and passed.
  7. A marker is written.claude/.e2e-pending/<session_id>.json — keyed by session, so one agent's pending run never blocks another's turn. Carries repo, branch, trigger, mode, commands, features, fallback, unmapped.
  8. The Stop hook blocks the turn — exactly oncenudged flips to true before the block is emitted, so a crash can only lose a nudge, never wedge the session in a loop nobody can escape.

The nine features it can select

attendance · coaching · language · lesson-plan · menu · observe · registration · status · training

Ignored everywhere: tests, docs, scripts, dashboard, assets, fonts, *.md, package-lock.json, mocks and snapshots. Changing only those selects nothing.

Switches

export E2E_AUTORUN_OFF=1     # disarms everything
export E2E_SPEC_SYNC_OFF=1   # drops phase 1 only — the E2E half is untouched
export E2E_AUTORUN_ALL=1     # arm /niete-e2e all instead of a targeted run
                             #   100 scenarios; coaching alone is ~2.5h

# clear a pending marker
bash .claude/hooks/e2e-autorun.sh --clear --session <session_id>

All three must be exported. An inline VAR=1 cmd is invisible to hooks. E2E_SPEC_SYNC_OFF is deliberately separate from E2E_AUTORUN_OFF: if spec authoring turns noisy, it must not take the E2E half down with it.

What it cannot do

Drive WhatsApp itself

The Chrome DevTools MCP tools belong to the agent, not to a hook subprocess. The hook can only put the order in front of you.

Know the deploy finished

A push-armed run fires the instant the push returns, while the build is still going. Confirm it's live first or you test the old build and pass.

Test what you just committed

A commit deploys nothing. A commit-armed run is a regression check on what was already live — the marker says so, and so should your report.

Guarantee a testable target

A linked WhatsApp Web session is a physical precondition. Navigate to web.whatsapp.com and look — list_pages alone cannot tell you a session is missing.

Two traps, both measured

The 120-second window breaks the hook's own tests

Pushing from the root checkout makes $PWD “freshly pushed”, so temp-repo test cases resolve to the worktree. 11 of 123 assertions failed immediately after a push and all passed again 127 s later. Don't run the suite within two minutes of a push.

wa-drive reports false timeouts

The message list is virtualized — measured n=36 before and after a send plus reply — so rows.length > base.n never fires. Detection falls to text equality, and row text carries only minute-resolution timestamps. An identical reply inside one clock minute is invisible and the wait runs to timeout.
