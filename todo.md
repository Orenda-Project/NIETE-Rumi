## STEP 6 — the deploy gate, and a hard ordering constraint

**The migration MUST be applied BEFORE the code deploys. Verified, not assumed.**

Probed against the live DB 2026-09-09:

| Operation | Without V1.4.2 | Contained? |
|---|---|---|
| `UPDATE ... answer_key_r2_key` (orchestrator) | `PGRST204` rejected | **Yes** — inside the answer-key try/catch, and `_patchPaper` swallows. Degrades to "no answer key", paper unaffected. |
| `SELECT ... answer_key_r2_key` (browse svc ×2) | `42703` rejected — **the whole query** | **No.** PostgREST fails the entire select for one unknown column, so `paperDownloadUrl` and `listPapers` return nothing. Downloads and My papers break outright. |

So the order is: **migration → verify column → deploy code.** Deploying first
does not merely degrade the feature, it breaks the two endpoints a teacher uses
to get her paper back.

### The bit that needs the operator

**NIETE-Rumi has ONE Supabase project (`ihzciabopbttygxxgrkm`, `rumi-niete`).
Staging and production share it.** There is no second ref anywhere in the repo
or its migration docs. So applying V1.4.2 "to staging" IS a production DB write
and needs an explicit per-action go — the staging pre-authorisation in
CLAUDE.md covers deploys, not prod-DB writes.

The change itself is additive and reversible: one nullable TEXT column, no
backfill, no constraint, no index. `ADD COLUMN IF NOT EXISTS` so it is safe to
re-run. Nothing reads it until the new code ships.
